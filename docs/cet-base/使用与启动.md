# 四六级底座 · 使用与启动

> 适用版本：分支 `codex/cet-listening` 集成后的四六级专用底座
> 实测平台：macOS 27.0.1 (Apple Silicon) · Python 3.11.16 · FFmpeg 9.0.2 · Chromium (Playwright)
> 未测平台：Windows / Linux / 移动端 —— 本版本只交付**本机可运行源码**，未做多平台打包。

本文所有命令都在**仓库根目录**执行，且经过实测。如果你照抄某条命令得不到文中结果，
请先看 [§7 排错](#7-排错)。

---

## 1. 这个版本是什么

EchoLingo 的四六级**听力**专用底座。核心链路：

```
打开应用 → 选四级/六级 → 看已有材料或导入本地音频 → 打开听力工作区
→ 播放 / 拖动 / 倍速 / 逐句 → 看原文、查词、收藏 → 返回材料库 → 再次进入恢复进度
```

**这条链路在无 AI key、未接队友模块时独立可用。**

本版本**不包含**（属队友模块或后续集成）：
空格卡点定位、AI 带练、换句检验、智能复习；也不做作文批改/翻译训练/口语评分。

## 3. 启动

### 3.1 一条命令（推荐）

```bash
scripts/cet/run.sh
```

脚本会依次做：环境检查 → 端口检测 → 数据隔离检查 → 材料检查 → 前端接入检查
→ 导入材料（幂等）→ 启动服务 → 打印**真实**的材料链接。

成功时输出类似：

```
==================================================================
  已启动

  六级材料   http://127.0.0.1:5173/workspace/1
  四级样例   http://127.0.0.1:5173/workspace/2
  首页       http://127.0.0.1:5173/
  接口       http://127.0.0.1:5173/api/cet/materials
  模式配置   http://127.0.0.1:5173/api/cet/mode

  停止       PORT=5173 scripts/qa/stop_cet.sh
  自验       .venv/bin/python scripts/cet/verify_base.py --port 5173
==================================================================
```

> **链接里的 `/workspace/1`、`/workspace/2` 是从数据库自增 ID 反查出来的，不是写死的。**
> 换库、换机器都会变，脚本每次都重新查。查不到会明确打印「未导入」，不会给假链接。

### 3.2 换端口（多人同机必读）

本机 5173 可能已有别的实例在跑。换端口：

```bash
scripts/cet/run.sh --port 5184
# 或
PORT=5184 scripts/cet/run.sh
```

`run.sh` 的端口检测有**三重判据**，不会误连别人的服务：

1. 端口是否有人监听；
2. `/health` 是否返回本项目形状；
3. **它报告的 `sqlite.path` 是否和本次要用的数据库是同一个**。

第 3 条是实测踩坑后加的。本机 5186 上曾有一个旧实例跑 `/tmp/cbroute/vocab.db`，
只看前两条会误判成「自家底座」而复用它，结果打开的是空库、和指定数据目录完全不符。
现在库不同会明确拒绝：

```
[X]  端口 5186 上已有一个底座，但用的是**另一个数据库**，拒绝复用：
     它 在用：/tmp/cbroute/vocab.db
     本次要：/tmp/cb-e2e/vocab.db
     复用会导致「连上了却看不到本次的数据」。请换端口：
       scripts/cet/run.sh --port 5184
     或先停掉旧实例：
       PORT=5186 scripts/qa/stop_cet.sh
```

### 3.3 空库启动

```bash
scripts/cet/run.sh --fresh --port 5184
```

`--fresh` 清空隔离库并**跳过材料导入**，用于验证「空库时首页可用、有导入入口、
无虚假加载」。此时材料列表返回 `{"items":[],"count":0}`，页面不报错。

清库前会先确认没有活服务持有该库（见 [§3.7](#37-清库前会先验所有权与停服状态)）：
被活服务持有时**拒绝执行并返回 3**，不会把正在跑的服务的库抽走。

要连整个数据目录一起重建（含 `config/`）：

```bash
scripts/cet/run.sh --reset --data-dir /tmp/cet-demo --port 5184
```

`--reset` 的 `rm -rf` 同样只在「检查通过 + 所有权与停服状态都确认」之后执行，
且**在 `--check` 模式下绝不执行**。

### 3.4 已有库启动

直接 `scripts/cet/run.sh`。材料导入是幂等的：已有材料复用不重复建，
学习进度与收藏保留。

### 3.5 指定数据目录

```bash
scripts/cet/run.sh --data-dir /tmp/my-cet-data --port 5184
# 或
ELT_DATA_DIR=/tmp/my-cet-data scripts/cet/run.sh --port 5184
```

每个数据目录自带 `vocab.db` 与 `config/`，互不影响。

### 3.6 只检查不启动（纯只读，零副作用）

```bash
scripts/cet/run.sh --check
```

**`--check` 是纯只读路径：不建目录、不删库、不动 WAL/SHM、不导入材料、不起服务。**
即使同时给了 `--fresh` 或 `--reset`，清理动作也会被跳过并明确打印出来：

```bash
scripts/cet/run.sh --check --fresh --data-dir /tmp/my-cet-data
#   [OK] 只检查模式：不删除任何数据（--fresh/--reset 的清理已跳过）
#        本次没有删除或修改任何数据库文件。
```

这条是返修 BASE-04-A 的产物。修复前 `--check --fresh` 会先删掉目标库再报「检查通过」，
验收方用临时 sentinel 库实测复现过（[独立验收报告 §BASE-04](../acceptance/2026-11-05-79e9e56-底座独立验收.md)）。

### 3.7 清库前会先验所有权与停服状态

`--fresh` / `--reset` 属于破坏性操作，脚本在执行前做三项确认：

1. **所有权**：目标库不是 `resources/vocab.db`（正式库）；数据目录不是仓库/家目录/根目录；
   已有文件必须是 SQLite 格式。
2. **停服状态**：没有任何活服务正在使用该库（三道判据，见下）。
3. 任一条不满足就**拒绝执行并返回 3**，一个字节都不删。

#### 「谁在用这个库」怎么判（三道判据，按可靠性排序）

| 判据 | 做法 | 为什么需要它 |
| --- | --- | --- |
| **health**（主） | 枚举所有活着的本项目底座进程，向它们的监听端口请求 `/health`，比对 `environment.sqlite.path` | **不依赖文件句柄**。本应用每请求开/关 SQLite 连接，服务空闲时 lsof 一个句柄都看不到 |
| **lsof**（辅） | 该进程是否打开着目标库的 DB/WAL/SHM | 服务正忙时更快，且能覆盖非本项目进程 |
| **instance**（辅） | 实例登记声明该库 + PID 存活 + 确实是本项目底座 | 覆盖「进程活着但还没开始监听」的启动瞬间 |
| **保守兜底** | 有活底座，但**问不出**它用哪个库 → 拒绝 | 宁可拒绝不可误删 |

> **为什么必须有 health 判据（真实踩坑）**：
> 本应用是每请求开/关 SQLite 连接（`db._db()` 上下文管理器）。服务刚启动、
> **还没处理过任何请求**时，`lsof -p <pid>` 返回 **0 个** `vocab.db` 句柄。
> 只查文件句柄的护栏在这个窗口里会判定「没人用这个库」→ **把活服务的库删掉**。
> 而 `run.sh` 的典型用法正是「刚起服务 → 想重置数据 → `--fresh`」，
> 这个时序是真实高频路径，不是理论边界。
>
> 实测：零请求的空闲服务 `lsof` 0 个句柄，但 `/health` 仍能报出
> `sqlite.path = /tmp/xxx/vocab.db`。所以 `/health` 才是可靠判据。

拒绝时输出：

```
-- 6. 数据目录写入（修改阶段）--
  [!]  以下活服务正在使用该库 —— 拒绝清库：
       PID 30056  端口 52973  （判据：health）
     先停掉它们：PORT=<端口> scripts/qa/stop_cet.sh
==================================================================
  拒绝执行：数据库仍被活服务使用，不能执行 --fresh/--reset
  本次没有删除或修改任何数据库文件。
==================================================================
```

确认无活服务时输出：

```
  [OK] 已确认没有活服务使用该库（/health 路径比对 + 文件句柄 + 保守兜底）
  [OK] 已清空隔离数据库（--fresh，清库前已确认无活服务持有）
```

这是返修 BASE-04-B 的产物。修复前「同库服务复用判断」在删库之前，
可能先认定「复用这个活服务」、随后又删掉它的 DB/WAL/SHM。

> **注意**：护栏只拦「同一个库」。别的库上有活服务（哪怕空闲）**不会**拦你清当前库 ——
> 判据是库，不是「有没有服务在跑」。

### 3.8 手动启动（想看日志 / 调试）

```bash
export ELT_USER_DB=/tmp/cet-demo/vocab.db
export ELT_CONFIG_DIR=/tmp/cet-demo/config
export ELT_PORT=5184
.venv/bin/python backend/fastapi_server.py
```

前台运行，Ctrl-C 停止。

### 3.9 停止（按实例，核验身份）

```bash
PORT=5184 scripts/qa/stop_cet.sh          # 只停端口 5184 上的那个实例
PORT=5184 scripts/qa/stop_cet.sh --list   # 先看有哪些实例在跑
PORT=5184 scripts/qa/stop_cet.sh --all    # 身份核不上时按端口强制停（危险，需明确）
```

**每个「端口 + 数据目录」是一个实例，各自有一份记录**：

```
.cet-qa/logs/instances/<端口>/server.pid     # 该实例的 PID
.cet-qa/logs/instances/<端口>/instance.env   # 端口 / PID / 数据库 三者绑定
```

停止前逐项核验身份，核不上就拒绝，**绝不误杀别的实例**：

| 核验 | 不通过时 |
| --- | --- |
| 该 PID 是否真的监听目标端口 | 跳过，不当候选 |
| 该进程是否**本项目底座**（`backend/fastapi_server.py`） | 拒绝停止（端口上可能是别人的服务） |
| 该进程用的库是否就是实例登记的库（`/health` 的 `sqlite.path` 或 lsof 文件句柄） | 拒绝停止 |

退出码：

| 码 | 含义 |
| --- | --- |
| 0 | 已停止，且端口确认已释放 |
| 1 | 端口仍被占用（未能干净停止） |
| 3 | 身份不符，拒绝停止（**没有任何进程被误杀**） |

这是返修 BASE-04-C 的产物。修复前所有实例共用一个 `.cet-qa/logs/server.pid`：
对实例 A 执行 `PORT=A stop`，实际杀掉的是 PID 文件里的 B，A 还活着且退出码 0
（验收方实测）。

> 旧的共享 `.cet-qa/logs/server.pid` 仍会写，只为向后兼容；它只作**候选来源**，
> 永不单独作为停止依据。

## 4. 导入材料

### 4.1 界面导入（普通用户）

首页 →「导入听力材料」→ 选音频 → 填标题、级别（四级/六级）、素材类别 → 可选配套字幕 → 导入。

- **音频**：最低支持播放器可用的常见格式（mp3 / m4a / wav / aac / flac）。
  界面只列实际测过的类型，不承诺未测格式。
- **字幕**：优先 SRT（带时间轴）。仓库原有的句子 JSON 也兼容。
- **纯文本**：只作原文，**不伪造逐句时间戳**。此时工作区会明确显示「暂无逐句定位」，
  逐句相关按钮禁用。
- **仅音频**：可以导入、可以整段播放。没有 key 时**不会**强制排队转写。

### 4.2 SRT 示例

```srt
1
00:00:00,010 --> 00:00:03,490
It's getting late and we're both displaying signs of weariness.

2
00:00:03,550 --> 00:00:07,010
I think we should call it a day and meet again tomorrow morning.
```

校验规则（错误会指出**具体条目**，不会默默跳过损坏行还报成功）：

- 起止时间非负，`end > start`
- 时间轴顺序递增
- 不超出音频时长
- 文本非空

### 4.3 命令行导入样例（验收方用）

```bash
export ELT_USER_DB=/tmp/cet-demo/vocab.db
.venv/bin/python scripts/cet/import_materials.py --list   # 看有哪些材料
.venv/bin/python scripts/cet/import_materials.py --all    # 全导入（幂等）
```

ELT_CONFIG_DIR=/tmp/verify/config \

### 5.4 启动/停止脚本边界回归（BASE-04）

```bash
ELT_CONFIG_DIR=/tmp/verify/config \
  .venv/bin/python -m pytest tests/test_cet_base_startup.py -q
# 期望：19 passed
```

这一组只用 pytest 的 `tmp_path` 自建临时库与临时进程，**不会碰正式库、
不会碰主工作区的 `.cet-qa/logs`、也不会停别人的实例**。它守住四条契约：

| 契约 | 用例 |
| --- | --- |
| `--check` 零副作用（不删库 / 不动 WAL-SHM / 不建目录 / 不碰正式库） | `test_check_fresh_does_not_delete_sentinel_db` 等 5 个 |
| 清库前验所有权与停服状态（活服务持库时拒绝并返回 3） | `test_fresh_refuses_when_service_holds_same_db_on_same_port` 等 4 个 |
| **空闲服务（零文件句柄）也必须被识别** | `test_fresh_refuses_when_idle_service_holds_no_file_handle` |
| 停止按实例核验身份（不误杀、不靠共享 PID 文件） | `test_stop_targets_requested_port_not_shared_pidfile` 等 6 个 |

> **关于「空闲服务」那条用例**：它用 `probe=False` 起后端（只等启动日志、
> 一个 HTTP 请求都不发），先断言 `lsof` 真的看不到句柄，再用**另一个端口**
> 跑 `--fresh` —— 两个条件缺一不可，否则检查阶段的 `/health` 探测会顺手打开
> 连接、把漏洞掩盖掉。这正是「时间窗口漏洞」当初没被其他用例抓到的原因。

## 6. ⚠️ 验收方注意：`ELT_USER_DB` 与 pytest 的冲突

**这一节很重要，踩了会得出完全错误的结论。**

### 6.1 现象

如果你用 `ELT_USER_DB` 跑 pytest：

```bash
# ❌ 错误用法
ELT_USER_DB=/tmp/x/vocab.db ELT_CONFIG_DIR=/tmp/x/config \
  .venv/bin/python -m pytest -q
```

会得到 **41 failed / 559 passed**。但这些失败**几乎全是假的**，不要写进验收报告。

### 6.2 原因

`backend/db.py` 的数据库路径是三级解析，**环境变量优先级高于模块属性**：

```python
def current_db_path() -> Path:
    p = _current_db_path.get()          # ① contextvar
    if p is not None:
        return p
    env = os.environ.get("ELT_USER_DB") # ② 环境变量  ← 优先级高于 ③
    if env:
        return Path(env)
    return DB_PATH                      # ③ 模块级默认（monkeypatch 改的是这个）
```

而绝大多数测试用 `monkeypatch.setattr(db, "DB_PATH", tmp_path/"vocab.db")` 做隔离 ——
**这改的是 ③，改不动 ②**。一旦设了 `ELT_USER_DB`，所有测试写进同一个库，
前一个用例的数据残留到后一个用例，产生大量「断言多了一条/少了一条」的假失败。

### 6.3 证据

同一个文件、同一个 SHA，只差一个环境变量：

```bash
ELT_CONFIG_DIR=/tmp/x/config .venv/bin/python -m pytest -q tests/test_vocab_review.py
# → 23 passed

ELT_USER_DB=/tmp/x/a.db ELT_CONFIG_DIR=/tmp/x/config \
  .venv/bin/python -m pytest -q tests/test_vocab_review.py
# → 10 failed, 13 passed
```

### 6.4 正确做法

| 用途 | 是否设 `ELT_USER_DB` |
| --- | --- |
| **跑 pytest** | ❌ 不设。只设 `ELT_CONFIG_DIR` |
| **起服务做数据隔离** | ✅ 设。这是它的正确用途 |

```bash
# ✅ 跑测试
ELT_CONFIG_DIR=/tmp/verify/config .venv/bin/python -m pytest -q

# ✅ 起服务
ELT_USER_DB=/tmp/cet-demo/vocab.db ELT_CONFIG_DIR=/tmp/cet-demo/config \
  .venv/bin/python backend/fastapi_server.py
```

## 7. 排错

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `未找到虚拟环境解释器 .venv/bin/python` | 新克隆仓库，`.venv` 不入库 | 按 [§2.1](#21-依赖) 建虚拟环境 |
| `端口 5173 已被其它进程占用` | 已有实例 | `--port 5184` 换端口 |
| `端口 ... 用的是另一个数据库，拒绝复用` | 旧实例 + 不同数据目录 | 换端口，或先 `PORT=<旧端口> scripts/qa/stop_cet.sh` |
| `拒绝执行：数据库仍被活服务使用`（退出码 3） | 该库正被活服务持有，`--fresh/--reset` 被拦 | 先停服务：`PORT=<端口> scripts/qa/stop_cet.sh`；确认后再跑 |
| `底座：... 不是本项目底座 —— 拒绝停止`（退出码 3） | 目标端口上跑的是别人的服务 | 换端口，或确认后用 `--all` |
| `底座：... 不监听端口 ... —— 不是本实例` | 共享 PID 文件里是别的实例 | 正常行为；用 `--list` 看真实实例 |
| `底座：... 但用的是 ... 不是本次目标 ... —— 拒绝停止`（退出码 3） | 实例记录与实际不符 | 用 `--list` 核对；必要时 `--all` |
| 停止脚本退出码 1 | 端口仍被占用，没干净停掉 | 看输出里的 lsof 行；`--all` 或手工处理 |
| `缺少 ffprobe` | 没装 FFmpeg | `brew install ffmpeg` |
| 材料链接显示「未导入」 | 空库或媒体文件缺失 | 放好 `.cet-qa/media/` 文件后重跑 `run.sh` |
| 页面标题仍是「英语精学工作台」 | 首页板块尚未交付收束 | 已知缺陷，见 `自验报告.md` |
| 工作区 console 有 409 | `/api/v2/lessons/{id}/reading` 在无翻译时返回 409 | 已知缺陷 B15，不影响播放与原文 |
| pytest 跑出 41 failed | 误设了 `ELT_USER_DB` | 见 [§6](#6-️-验收方注意elt_user_db-与-pytest-的冲突) |

## 8. 目录与数据
