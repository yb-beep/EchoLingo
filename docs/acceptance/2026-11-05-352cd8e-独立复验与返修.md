## S1 · P1 · 最新反馈已入库，但模型实际收到上一次反馈

**实测：真实 API + 受控模型入口记录。**

顺序：创建练习 → sound → 当前步骤 meaning → 当前步骤 heard。

- meaning 返回 200，latestFeedback=meaning；实际 `cet_ai._call` 收到 action=explain、feedback=sound。
- heard 进入换句；实际模型入口收到 action=transfer、feedback=meaning。
- 页面另一次首次点击“不懂意思”时，模型收到 feedback 空字符串。

根因：`backend/webapp/services/cet_service.py:1334` 读取 practice 行；1341 更新数据库后，仍用旧行对象的 latest_feedback 组装 1361 的 request_data 和 1385 的 generate 参数。

证据：[模型入口日志](./evidence/352cd8e-independent/model-input.jsonl)、[API 复现](./evidence/352cd8e-independent/api-probe.json)、[复现脚本](./evidence/352cd8e-independent/probe.py)。日志只记录动作与反馈，无凭据。

**返修标准：**使用本次合法反馈，或在同一事务中更新后重新读取一致的状态；模型调用参数、AI 请求记录、latestFeedback 三者必须一致。补“第一次 meaning”“sound→meaning”“meaning→heard”断言，测试应捕获模型入口实参，不能只检查数据库。

## S2 · P1 · 仍有独立 commit，并发交错后 409 仍留下反馈

证据：[交错结果](./evidence/352cd8e-independent/interleave.json)、[可重跑脚本](./evidence/352cd8e-independent/controlled-checks.py)。脚本使用独立 interleave.db；请先运行 probe 生成本轮前置记录。

## S6 · P2 · 同一练习的迟到响应仍缺少前端保护

源码检查，**本轮未做网络乱序实测**：JS:529 只检查 practiceId，随后直接覆盖 S.practice；同一练习先后两个请求如果在服务器依次成功、响应在网络中乱序，后到的旧成功仍可能覆盖最新步骤。catch 也只比较练习身份；submitTransferAnswer 的成功合并没有身份过滤。

不能认为“后端会返回 STALE_RESPONSE”覆盖所有前端响应顺序。应增加请求序号/当前步骤/版本校验，成功和失败统一保护，补可控乱序测试。等待区挂载通过不等于 R5 的并发与恢复要求全部通过。
