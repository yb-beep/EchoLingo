## 2. 材料身份与元数据（P1）

### 2.1 身份规则

| 概念 | 规则 |
| --- | --- |
| 底座 lesson id | `v2_lessons.id`，页面路由 `/workspace/<id>` |
| 业务 materialId | 由 `source_url` 派生（`file://cet6-202512-conv2.mp3` → `cet6-202512-conv2`） |
| 回退 | 派生不出时用 `v2-<lesson_id>`（`fixture://`、`upload:` 前缀不派生，因为换机器就变） |

**不依赖硬编码 lesson 数字**：同一份材料换库、换自增 ID，业务 ID 不变。

### 2.2 级别：只认 tags，不猜标题

```
tags 含 cet6 或 六级  → cet6
tags 含 cet4 或 四级  → cet4
其他（含空/坏 JSON）  → unspecified（= 待分类）
```

**明确不做**：按标题关键词推断级别。标题写着「2025年12月六级第一套」但没有
级别标签的材料，仍然是 `unspecified`——它可能是练习、可能是转载，不能替用户认级别。

### 2.3 素材类别：只认显式登记

`真题` / `练习` / `样例` / `开发夹具`，来源仅两处：

1. `tags` 里的显式类别标签（如 `["cet6", "真题"]`）
2. 显式夹具来源标记（`source_type` ∈ `developmentFixture`/`fixture`，或 `source_url` 以 `fixture://` 开头）

**明确不做**：从标题推断「真题」身份。任务书 §1 已指出
`cet4-sample-hope-wish` 是难度样例、不是已核实的四级真题；
标题含年份/月份/套次不构成真题证据。取不到 → `None`，前端显示「未标注」。

### 2.4 可用状态：如实回报，缺失即缺失

| 字段 | 含义 | 缺失时 |
| --- | --- | --- |
| `hasAudio` | 声明了 `media_url` | `false` |
| `audioReachable` | `media_url` 对应文件**本机真实可读** | `false` |
| `hasTimeline` | 有逐句字幕段 | `false` |
| `sentenceCount` | 字幕段数 | `0` |
| `questionCount` | 题目数 | `None`（表不存在=未知，**不是 0**） |
| `subtitleStatus` | 原样回显 `v2_lessons.subtitle_status` | `""` |
| `audioSha256` | 实际读取音频文件计算 | `""`（文件不可读不编造） |

`hasAudio` 与 `audioReachable` **分开**：前者是「材料声明有音频」，
后者是「此刻真能播」。两者不一致时前端才能给出准确反馈。

### 2.5 搜索 / 最近学习 / 继续学习

- **搜索**：标题 + materialId + tags 子串匹配，大小写不敏感。
- **最近学习**：`list_materials()` 默认排序沿用 `db.list_v2_lessons()` 的
  `progress.updated_at → lesson.updated_at → created_at` 倒序。
- **继续学习**：`only_started=True` 只返回 `v2_lesson_progress` 有记录的材料。

全部基于现有 `v2_lesson_progress`，**不新建表**。

### 2.6 待分类与手动归类

`library_summary()` 返回各级别数量 + `pendingClassification` 数量与 lesson id 列表。

归类写 `v2_lessons.tags`（冻结约定 §3 只允许现有列）：

```python
cet_materials.update_material(lesson_id, level="cet4")   # 写 cet4 标签
cet_materials.update_material(lesson_id, level="unspecified")  # 退回待分类
cet_materials.update_material(lesson_id, category="练习")       # 写类别标签
cet_materials.update_material(lesson_id, category="")           # 清除类别
```

**用户自己的其他标签保留**，只替换级别/类别这两类受管标签；
重新归类时旧级别标签被移除（一份材料不能同时属于四级和六级）。

**PATCH 未传字段一律保留原值（BASE-01 返修）**：

| 传入 | 效果 | 未传的字段 |
| --- | --- | --- |
| `level="cet6"` | 只替换级别标签，**类别标签原样保留** | `category`/`title`/`archived` 不变 |
| `level="unspecified"` | 只删级别标签（退回待分类），**类别保留** | 同上 |
| `category="真题"` | 只替换类别标签，**级别标签原样保留** | `level`/`title`/`archived` 不变 |
| `category=""` | 只删类别标签，**级别保留** | 同上 |
| `title="新标题"` | 只改标题，`tags` 一个字节都不重写 | 其余不变 |
| `archived=true/false` | 只改归档位，`tags` 不动 | 其余不变 |

> **为什么必须这样**：旧实现一进 `update_material()` 就 `_strip_managed_tags()`
> 把级别与类别标签**全部删掉**，然后只重建本次请求传入的字段。首页「手动归类」
> 只提交 `level`，于是六级/样例材料点一下「仍填六级」就变成「六级/未标注」，
> 样例类别凭空丢失；反方向只改 `category` 又把级别变成 `unspecified`。
> 现在只重写本次显式传入的那一类标签（`_strip_level_tags` / `_strip_category_tags`
> 分开），并且**所有校验先做完再写库**，任一项不合法就整体不写，不会出现半改。
>
> 回归测试（`tests/test_cet_base_materials.py`）：只改级别、只改类别、只改标题、
> 只归档四条互不串改场景 + 一条同时改级别和类别 + 一条明确清空 + 一条非法值不半写
> + 一条 HTTP 路由等价场景。

### 2.7 归档可恢复

`archived=True/False` 写现有 `v2_lessons.archived`。
默认列表不含归档；`include_archived=True` 可见。
**归档不删任何数据**：字幕段、学习进度、题目全部保留（有测试断言）。

## 3. 本地导入（P2）

### 3.1 支持格式（全部实测，界面照此显示）

| 类型 | 扩展名 | 说明 |
| --- | --- | --- |
| 音频 | `.mp3` `.m4a` `.wav` `.ogg` `.flac` `.aac` | 与 `v2_lessons._AUDIO_EXTS` 一致 |
| 字幕（带时间轴） | `.srt` `.vtt` `.json` | 可逐句定位 |
| 纯文本原文 | `.txt` | 只作听力稿，**不生成逐句时间轴** |

> `.mp3/.m4a/.wav/.ogg/.flac/.aac` 六种格式均用 ffmpeg 真实转码后逐一导入成功
> （见 `test_every_declared_audio_format_is_accepted`，参数化 6 条）。
> 测试还断言 `SUPPORTED_AUDIO_EXTS == v2_lessons._AUDIO_EXTS`，防止多承诺。

### 3.2 字幕解析：不复用自动字幕解析器

**不复用** `sources/subtitle_parser.parse_subtitle_file` 作为主解析器。原因：
那个解析器是为「YouTube 自动字幕去重」设计的，会做滚动字幕合并、行级去重、
按标点重新切句——对**用户自己准备的规范 SRT**，这些变换会改变条目数和时间轴，
校验就失去意义了。

实测证据（`test_import_srt_stored_verbatim_not_resegmented`）：
一条 cue 内含两句 `First sentence. Second sentence in same cue.`
→ 落库仍是 **1 条**，不因标点被拆成 2 条。

### 3.3 校验规则与错误格式

| 规则 | reason | 示例 message |
| --- | --- | --- |
| 起止非负 | `negative_time` | 第 1 条（第 2 行）时间轴为负：-1.000 → 2.000 |
| `end > start` | `end_not_after_start` | 第 1 条（第 2 行）结束时间不大于开始时间：9.000 → 4.000 |
| 顺序递增 | `out_of_order` | 第 2 条（第 6 行）开始时间 1.000s 早于上一条（第 1 条）的结束时间 7.000s |
| 不超音频时长 | `beyond_audio` | 第 1 条（第 2 行）结束时间 90.000s 超出音频时长 60.000s |
| 非空文本 | `empty_text` | 第 1 条（第 2 行）文本为空 |
| 时间轴行缺失 | `not_a_timing_line` | 第 N 行不是合法的字幕时间轴（缺少 "-->"） |
| 时间戳不可解析 | `unparsable_timestamp` | 第 N 条（第 M 行）时间轴无法解析 |
| JSON 非对象条目 | `invalid_entry` | sentences 数组第 2 个元素不是句子对象（实际是 字符串「BROKEN」） |
| 音频文件无效 | `invalid_audio` | 文件不是有效音频：bad.mp3 无法被解析为音视频 |
| 音频超过大小上限 | `audio_too_large` | 音频文件过大（HTTP 413） |

**关键行为**：
- **逐条全报**，不是遇到第一条就停（实测一个文件 3 个错误全部返回）。
- **解析错误与校验错误合并返回**，用户一次看到全部问题。
- 任一条错误 → **整体拒绝**，不写半份材料、不留上传暂存。
- 相邻句 `end == 下一句 start` 合法（不算 `out_of_order`）。

**JSON 坏条目不再静默丢弃（BASE-02 返修）**：

旧实现 `_json_sentences()` 用 `[item for item in raw if isinstance(item, dict)]`
预先把非对象元素滤掉，于是 `[合法句1, "BROKEN", null, 合法句2]` 返回 200、
`errors=[]`、只落 2 句 —— 用户以为全部导入成功，被丢的两条毫无痕迹。

现在的规则：

- 非对象条目（字符串 / `null` / 数字 / 数组）逐条报 `invalid_entry`，
  错误里的 `index` 是**原始数组位置（1 基）**，不是过滤后的序号；
- 合法条目的 `index` 也保留原始位置（上例是 `1` 和 `4`，不是 `1`、`2`）；
- 有任何坏条目 → **整份导入拒绝**，不落任何句子、不建材料、不留暂存；
- 包装形态（`{"sentences": [...]}`）同样生效，错误消息带上数组名；
- `_json_sentences()` 保留给「不需要错误详情」的内部调用方，
  判断导入是否成功必须用 `parse_sentence_json()`。

`start: "NaN"` / `Infinity` 这类能通过 `float()` 但不是有限数的值，
现在在**预检阶段**就被报成 `unparsable_timestamp`（旧实现会冒到
SQLite 的 NOT NULL 约束才炸，错误变成 `import_failed` 且不指向条目）。

回归测试（`tests/test_cet_base_import.py`）：混合坏条目原始场景、
包装形态、预检端点、`parse_sentence_json` 位置保留、全合法不误伤、NaN 预检。

### 3.4 纯文本：不伪造时间戳

`.txt` 按空行分段，写进 `v2_reading_blocks`（`start_seconds`/`end_seconds` 为 `NULL`），
`v2_subtitle_segments` **保持为空**，`timed=False`。

断言见 `test_import_plain_text_never_fabricates_timestamps`：
`db.get_v2_subtitle_segments(lesson_id) == []`、`blocks[0]["start_seconds"] is None`。

### 3.5 仅音频：明确「暂无逐句定位」

可播放，`subtitle_status='unavailable'`，返回 warning
「仅导入了音频；暂无逐句定位（无时间轴），逐句回听不可用。」

**不排队 Whisper 转写**。这是刻意的：

- 任务书 §4 P2：「没有 key 时不得强制排队转写」
- 更严重的是竞态：`start_uploaded_media_lesson()` 末尾会
  `enqueue_local_import()` 排后台转写，转写完成后
  `db.replace_v2_subtitle_segments()` 会**覆盖用户提供的字幕**。

所以 `cet_import._create_lesson_from_upload()` 复用同一套原语
（原子 consume → 建课 → 复制媒体 → 失败回滚），但不排转写。
测试 fixture 把 `enqueue_local_import` 桩成抛错，被调用即 fail。

**但「默认不转写」不等于「永远不能转写」**：返修2 P3-1 加了**用户显式勾选**的
自动切句，默认关闭。详见 §3.10。

### 3.6 去重

**同音频 SHA-256 + 同标题** → 返回已有材料 `duplicate: true`，不建第二份。

- 同音频不同标题 → 不是重复（用户可能建两份不同用途）
- 同标题不同音频 → 不是重复
- 重复时不覆盖已有时间轴（有测试断言逐段相等）
- 需要强制再建一份时传 `allow_duplicate=True`

**查重与建课原子化（BASE-03 缺陷 A 返修）**：

旧实现查重与建课分离，同标题同真实音频的两个并发请求**都**查到「无重复」，
于是各建一份，双双返回 `duplicate=false`（实测 lessonId 4、5，列表 count=2）。

现在的分层：

1. **临界区外快路径查重** —— 已有材料直接返回，不必抢锁；
2. **临界区内权威二次查重** —— `_matching_lesson_ids()` 直接读数据库当前真实
   状态，不经过任何可被替换的公开函数；
3. **进程内按键互斥** —— 键是 `(数据库路径, 音频 SHA-256, 标题小写)`，
   多用户各自 `vocab.db` 之间不互相阻塞；最后一个使用者退出时清理注册表；
4. **建成后复核** —— 多进程/多实例部署下进程内锁不覆盖，建成后若发现
   id 更小的同键材料（另一实例先建成），本轮这份回滚并返回
   `duplicate=true` 指向先到者。

效果：并发两请求的结果恒为「一个 `duplicate=false` 真正建课 +
一个 `duplicate=true` 指向同一 lesson」，库里只有一份。
`allow_duplicate=True` 仍然可以显式再建一份。

回归测试：`test_concurrent_duplicate_import_creates_one_material`（复刻验收探针
在查重返回后插屏障的确定性交错）、`test_stale_duplicate_lookup_still_cannot_double_create`
（查重被绕过也不能建两份）、`test_allow_duplicate_still_creates_second_material`。

### 3.7 失败不留假卡片

建课中途失败（磁盘满、复制失败等）→ 删掉本轮建的 lesson 与资产，
上传记录恢复 `ready` 可重试。测试：
`test_lesson_creation_failure_rolls_back_and_keeps_upload_retryable`。

### 3.8 状态收敛（D-IMPORT-1）

```python
cet_import.finalize_lesson_status(lesson_id, has_timeline=True/False)
```

| 情况 | `subtitle_status` | `summary_status` |
| --- | --- | --- |
| 有逐句时间轴 | `ready` | `skipped` |
| 仅音频 / 纯文本 | `unavailable` | `skipped` |

**为什么不用 `pending`**：前端把 `pending` 当「字幕生成中」——会持续轮询
`/reading`、徽标显示「字幕生成中」、学习页初始态假称正在生成（违反任务书 §4 P3）。

**为什么不用 `failed`**：`failed` 会弹「字幕失败」错误弹窗并诱导用户重试转写，
而仅音频导入是**正常成功**的结果，不是失败。

`unavailable` 是独立终态：不轮询、不弹错，语义就是「暂无逐句定位」。

### 3.9 坏音频与异常映射（BASE-03 缺陷 B 返修）

旧行为：`bad.mp3`（内容 `b'not audio at all'`）返回 **500 + 纯文本
`Internal Server Error`**。原因是上传调用 `save_media_upload()` 在保护范围外，
它内部 ffprobe 校验抛 `MediaUploadError`，而路由只捕获 `ImportValidationError`。

现在分三层处理，**任何一层都不再漏出纯文本错误响应**：

| 层 | 位置 | 行为 |
| --- | --- | --- |
| 预检 | `import_local_material()` 调 `_audio_probe()` | ffprobe 判定不是音视频 → `invalid_audio`（422），**此时还没有任何暂存** |
| 上传 | `_create_new_material()` 包住 `save_media_upload()` | `MediaUploadTooLargeError` → 413；其它 `MediaUploadError` → `invalid_audio`（422） |
| 路由兜底 | `cet_base.py` | `MediaUploadError` → 结构化 4xx（第二道保险）；其它未映射异常 → **结构化 500** `IMPORT_INTERNAL_ERROR`，不吞栈（服务端仍留日志） |

> **语义分层（Lead 定案）**：校验类错误一律 4xx；程序异常保持 **500 + 结构化
> JSON**。理由：把程序 bug 谎报成 422 会让用户以为「我的文件有问题」，
> 掩盖真实缺陷；但纯文本 `Internal Server Error` 也确实不可接受。
> 任务书 §6 T05 要求的是「各自有清楚结果、无假成功」，**不是**
> 「所有异常都必须是 4xx」。

`_audio_probe()` 刻意区分两种失败，避免「环境缺 ffprobe 就拒绝所有导入」：

- `(None, "invalid_audio")` — ffprobe 能跑但判定不是音视频 → **明确拒绝**
- `(None, "probe_unavailable")` — ffprobe 缺失/临时文件异常 → **不据此拒绝**，
  只跳过「不超音频时长」这项校验

失败后的状态（有测试逐项断言）：**无假卡片**（`list_v2_lessons() == []`）、
**无上传记录**（`v2_media_uploads` 计数 0）、**uploads 目录干净**
（`list(uploads_root.iterdir()) == []`）。

回归测试：`test_invalid_audio_returns_structured_422_not_plain_500`、
`test_invalid_audio_leaves_no_material_and_no_upload_residue`、
`test_audio_probe_distinguishes_invalid_audio_from_missing_ffprobe`、
`test_probe_unavailable_skips_duration_check_only`、
`test_route_maps_unexpected_error_to_structured_json`、
`test_route_maps_media_upload_error_to_structured_422`、
`test_route_maps_too_large_to_413`。

### 3.10 本地模型自动切句（返修2 · P3-1，默认关闭）

真实真题最常见是「MP3 + 原文 TXT」。这种组合在返修前导入后是
`subtitle_status='unavailable'`（不能逐句听）。P3-1 加了一个**可选**能力：
导入面板勾「用本地模型自动切句（无需 API key）」。

**默认不勾**。不勾时全流程与返修前**逐字节一致**（现有 70 条
`test_cet_base_import.py` 守着，本包另有正面断言 `autoSplit.queued === false`）。

#### 三条硬约束（都有后端强制，不只靠前端）

| 约束 | 前端 | 后端 |
| --- | --- | --- |
| 默认不勾 | `checked` 不写；`cetResetImport()` 归零 | `auto_split: bool = False` 默认值 |
| 有用户字幕时不可勾 | `disabled` + 说明「会覆盖你上传的字幕时间轴」 | **422 硬拒**，`reason=auto_split_conflicts_with_subtitle` |
| `faster_whisper` 不可用时灰掉 | 读 `/import/formats` 的 `autoSplit.available` | 同一份探测；直接调 API 也 422 `auto_split_unavailable` |

「有字幕时禁用」是**从根上避开竞态**：不是「尽量别覆盖用户字幕」，
而是这条请求根本不允许存在。前端 disabled 只防「按正常路径点按钮的人」，
直接调 API / 脚本 / 并发请求都能绕过前端，所以后端必须再判一次。

#### 两条路径：有原文优先文本对齐

| 附件 | 路径 | 句子文本来源 |
| --- | --- | --- |
| 音频 + TXT | **文本对齐**（`text_alignment`） | **用户原文**（逐字不改，只补时间轴） |
| 仅音频 | **纯转写**（`transcribe`） | 本地 ASR 识别结果（可能有错字） |

实现：`_transcribe_words_local()` 取词级时间戳 →
`align_text_to_words()`（`difflib.SequenceMatcher` 对齐原文词序列与 ASR 词序列）
→ `build_segments_from_text_alignment()`。

**为什么不用 `start_local_lesson(transcript_path=...)`**（任务书提示的那条）：
那条路径最终走到 `sources.baidu.build_local_video_lesson()`，它用
`parse_subtitle_file(transcript)` 解析原文 —— 而那个解析器**只认 SRT/VTT 的
`-->` 行，喂纯文本返回空列表**（本轮实测：纯文本 → `[]`）。
所以「把 TXT 当 transcript_path 传进去」会得到一个空时间轴，
既不是文本对齐也不是转写，是个静默失败。这也是这里自己做
「原文 → 句子 → 词级投影」的原因。

#### 进度复用现有状态枚举（不新造）

| 阶段 | `subtitle_status` | 前端显示 |
| --- | --- | --- |
| 排队 / 转写中 | `pending` | 正在准备原文 |
| 成功 | `ready` | 可逐句精听 |
| 失败 | `failed` + `subtitle_error` 写具体原因 | 原文准备失败 |

**失败不弹「字幕失败」诱导重试**：`failed` 在材料卡上映射为「原文准备失败」，
`subtitle_error` 里是具体原因（「模型加载失败：磁盘空间不足」「课程音频文件不可读」
「本地模型没有识别出任何语音内容（录音可能全是静音）」等）。

**不写 `pending` 悬挂**：异常分支一定写 `failed`，不会让卡片永远停在「正在准备原文」。

#### 能力探测口径（毫秒级，不加载模型）

`auto_split_capability()` 判三件事：

1. `faster_whisper` 能否 `import`（用 `find_spec`，不真 import C 扩展）；
2. HF 缓存里该模型有没有**完整权重**（`model.bin` 非空）；
3. `ffmpeg` 是否可用。

**只看缓存目录存在是不够的**：本轮实测本机
`models--Systran--faster-whisper-small/snapshots/*/` 只有
`config.json`/`tokenizer.json`/`vocabulary.txt`，**没有 `model.bin`** ——
若按「目录存在」判断可用，转写会卡在联网下载（实测卡 11 分钟无进展）。
所以口径是 `model.bin` 存在且非空。缓存完整的是
`large-v3`（3.09 GB）与 `large-v3-turbo`（1.62 GB）。

默认模型选 `large-v3-turbo`（可用 `ELT_CET_AUTO_SPLIT_MODEL` 覆盖）：
本机实测 105s 音频 turbo 转写 41s，large-v3 约 3 倍慢，而切句只需要句边界。

#### 实测耗时（本机 Intel 10 核 / CPU int8）

| 场景 | 耗时 |
| --- | --- |
| 导入请求返回（不阻塞） | **0.15 s** |
| 105s 音频 + TXT 文本对齐（含模型加载 7.6s） | **约 45 s** 后变 `ready` |
| 105s 音频 turbo 纯转写（直接跑模型） | 41.2 s |

#### 元数据 sidecar（不新增列）

`output/v2_assets/<lesson_id>/auto_split.json` 记录
`{mode, path, textSource, sentenceCount, model}` —— 「这份时间轴是怎么来的」可追溯。
冻结约定 §3 禁止新增列，所以用 sidecar。

#### 回归测试

`tests/test_cet_fix2_p3_auto_split.py`（31 条）：默认不排队、有字幕硬拒（SRT/VTT/JSON）、
TXT 走文本对齐、仅音频走纯转写、`pending→ready/failed` 状态收敛、
失败给明确原因、能力探测三态、纯函数对齐（单调/覆盖率/无词返回空）。

#### 句子数口径（返修2 P3-2 修正后的实测数字）

> **文档句子数以接口实际返回为准**（任务书 P3-2 的明确要求）。
> 下表是 2026-11-06 在隔离库重导后的实测值，不是设计目标值。

| 材料 | `v2_subtitle_segments`（落库） | `/api/v2/lessons/{id}/subtitles` 的 `segments` | 同接口的 `sentence_units` | 一致？ |
| --- | --- | --- | --- | --- |
| `cet6-202512-conv2`（六级真题） | **32** | **32** | **32** | ✅ 一致 |
| `cet4-sample-hope-wish`（四级样例） | 32 | 32 | 35 | ⚠️ 不等（见下） |

**修前**：六级真题落库 32 条，但 `sentence_units` 是 **33** 条 ——
多出来的第 23 条是 `/ W: What?`。根因不是落库条数，而是
`cet6-202512-conv2.sentences.source.json` 第 22 条的 `text` 末尾**粘着下一位
说话人的整句**：

```
"When we are done with it and send it upstairs, what do you think will happen? / W: What?"
```

而第 23 条自己就是 `What?`。`build_translation_units()` 会把第 22 条按标点
再切一次，于是多出一条以 `/ W:` 开头的「句子」。这就是「文档 32 句 /
精听页 33 句」的真实来源。

**修后**：`prepare_subtitle()` 在解析后、校验前清洗说话人标记，
并做**标记回声去重**（拆出的尾巴若与下一条逐字相同 → 是回声，丢弃；
标记本身仍记入 `speaker_markers.json` sidecar）。六级真题 32 = 32 = 32。

**为什么四级样例是 32 / 32 / 35**：它本身**没有说话人标记**（清洗零改动），
35 是 `build_translation_units()` 既有的「一条 cue 内含多句 → 按标点再切」
行为（例如 `"Don't get me wrong—it's a great…"` 这类长句会被切）。
这是那个函数的设计（工作区一句 = 一个可循环的播放单元），
**不是本包的缺陷，也不是 P3-2 的目标**。所以
「文档句子数 = `sentence_units`」这个等式**只对没有说话人标记、
且 cue 内不含多句的材料成立**；报告句子数时应以
`segments`（落库条数）为准，`sentence_units` 是播放单元数。

回归测试：`test_real_cet6_fixture_has_no_marker_sentence`（断言 32=32=32）、
`test_subtitles_endpoint_unit_count_matches_segment_count`（HTTP 端到端）。

### 7.3 其它限制

- 题目（`cet_questions`）作为可选附件原样保留，本轮不做做题判分/证据诊断。
- 导入不生成译文、不调模型；无 key 完全可用。
- `.json` 字幕仅支持「句子数组」结构（`sentences`/`items`/`segments`/`units`），

- 音频大小上限沿用现有 `ELT_MEDIA_UPLOAD_MAX_MB`（默认 500 MB）。
- 去重键是「音频 SHA-256 + 标题」，不比对字幕内容：同音频同标题但换了字幕，
  会判为重复、不覆盖（避免误改用户已有材料；需覆盖时用 `allow_duplicate=True` 新建）。

### 7.4 导入去重：当前是单 worker 部署假设（Lead 定案，已知限制）

**当前实现**（BASE-03 缺陷 A 修复，`cet_import.py`）：

1. 进程内按键互斥 `_dedupe_guard()`（键 = 数据库路径 + 音频 SHA-256 + 标题小写）
2. 临界区内权威二次查重 `_matching_lesson_ids()`（读真实 DB 状态）
3. 建成后复核（多进程兜底：发现 id 更小的同键材料则回滚本轮、返回先到者）

**已知限制：去重保护只在单 worker 部署下严格成立。**

- 第 1 层（进程内锁）只覆盖同一进程。**多 worker（uvicorn `workers>1`、
  多实例、容器副本）下互斥失效**，两个 worker 可能同时进入建课流程。
- 第 3 层（建成后复核）能兜住大部分并发，但它是**事后补偿**：
  败者会先真实建出一份再回滚删除，存在极短窗口内两份并存、
  且并发进程数 >2 时 id 大小比较不保证唯一裁决。
- 之所以没做成数据库唯一约束：去重键是「音频 SHA-256 + 标题」的**组合派生值**，
  `v2_lessons` 现有列里没有可直接建唯一索引的字段，而冻结约定 §3 规定
  **不得为元数据新增表或列**（级别/类别/去重都只能用现有列）。

**多 worker 部署前必须做的事**（需 schema 变更评审，不在本轮范围）：

1. 在 `v2_lessons` 增加一个派生的去重键列（例如 `dedupe_key TEXT`，
   写入 `sha256(audio_sha256 + "\x00" + lower(title))`），或新建
   `v2_lesson_dedupe` 映射表；
2. 对该列建 `UNIQUE` 索引，建课走「先插键、再建课」的 claim 语义；
3. 冲突时按唯一约束异常回退成 `duplicate=true` 返回已有 lesson。

**本轮口径（独立验收若问起，按此回答）**：单 worker 部署下已通过并发实测
（同标题同真实音频两并发请求 → 恒为一个 `duplicate=false` + 一个
`duplicate=true` 指向同一 lesson，库中 count=1）；多 worker 场景明确**不在
本轮承诺范围**，记录为本已知限制。

### 8.5 返修中确立的两条实现原则

**① 先校验全部字段，再写库（避免半改）**

`update_material()` 现在的顺序是：先把 `level` / `category` / `title` 全部归一与
校验完，任何一项不合法就在**写库之前**抛错；确认全部合法后才依次写 tags、
标题、归档位。

旧实现是「校验一项、写一项」交错：`PATCH {level:"cet4", category:"随便写的"}`
会先把级别改成 cet4，再在类别校验处抛错 —— 用户看到 422，但级别已经变了，
处于**级别已改、类别未改的半写状态**，比直接失败更难排查。

这条原则比验收方 BASE-01 的原始要求更彻底：验收方只要求「未传字段保留」，
但「传了非法值」同样不能留下半改结果。回归测试
`test_patch_invalid_value_does_not_partially_write` 断言非法组合后
`tags` 与 `level`/`category` 一字未动。

**② 语义分层：校验错误 4xx，程序异常 500 + 结构化 JSON**

见 §3.9。不把程序 bug 谎报成 422，也不让任何异常退化成纯文本响应。
