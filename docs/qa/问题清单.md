### BUG-006e · 错误响应存在两种形状，A 只处理一种会白屏

| 字段 | 内容 |
| --- | --- |
| 严重度 | **P2**（不阻断后端，但会让前端错误处理半失效） |
| 状态 | ⚠️ **非缺陷，属 FastAPI 既有行为** → 已写入契约并加以约束 |
| 归属 | C（契约说明）；A 需按约定处理 |

**现象**：C 实测所有 CET 端点，错误响应会出现两种结构：

```
业务校验失败  → {"error": "...", "error_info": {code, title, action, ...}}
请求体解析失败 → {"detail": [{"type": "dict_type", "msg": "Input should be a valid dictionary"}]}
```

**为什么算问题**：A 若只按 `error_info` 写错误处理，遇到请求体解析失败（`detail` 形状）
就会拿不到可显示的信息，页面表现为白屏或「未知错误」。

**这不是缺陷**：第二种形状是 FastAPI 的默认 `RequestValidationError` 响应，
拦截它需要自定义 exception handler。底座既有前端已经兼容两种
（`frontend/static/elt_credits.js:63` 用 `payload.detail || payload.error_info || payload`），
说明这是既定做法，不是 bug。

**处理**：
1. 在给 A 的对接说明里写清两种形状与推荐解析规则（照底座的做法）；
2. 加契约测试 `test_error_response_is_parseable_by_one_rule`，
   保证**所有错误响应都能被同一条规则解析出可显示信息**，
   不允许出现三种字段都没有的裸错误体；
3. 加 `test_malformed_json_does_not_crash`：畸形请求体不得 5xx
   （5xx 只能显示「服务器错误」，对用户无意义）；
4. 加 `test_not_found_does_not_leak_internal_paths`：错误信息不得泄露本机绝对路径
   （交付物与演示截图会暴露机器信息）。

**复验**：把 Mock 的 reviews 端点改成对空体抛 500 后，
`test_malformed_json_does_not_crash` 立刻失败；恢复后 56 项全通过。

### BUG-006b · Mock 交卷并发下产生多个 attemptId（TOCTOU 竞态）

| 字段 | 内容 |
| --- | --- |
| 严重度 | **P1**（会让前端联调时出现重复记录，且难复现） |
| 状态 | ✅ **已复验**（C 修复） |
| 归属 | C（Mock 实现） |

**发现方式**：补并发测试时暴露。`test_concurrent_attempts_create_one_record` 在整套测试里**约 1/12 概率失败**，单独跑却总通过 —— 典型的并发特征「平时都对，压一下就错」。

**根因**：`submit_attempt` 是「先查 `STATE["attemptBySession"]`，不存在再写入」的 check-then-act。FastAPI 的同步路由跑在线程池里，两个请求可能**同时通过存在性检查**，各自生成 attemptId 并覆盖写入。

**修复**：引入 `_STATE_LOCK = threading.RLock()`，把「查重 → 生成 ID → 写 attempts → 写 attemptBySession」整段放进同一把锁。同类竞态一并修了：
- `create_mark`：eventId 去重与写入
- `practice_event`：eventId 幂等判断与 effectiveMs 累加

**证据与复验**：

| 项 | 修复前 | 修复后 |
| --- | --- | --- |
| 全量测试 12 轮 | 1 次失败 | — |
| 全量测试 **25 轮** | — | **0 次失败** |

```
修复前：9: 1 failed, 43 passed in 2.85s   ← 1/12 概率
修复后：25 轮全量，失败 0 次
```

**对真实后端的意义**：这是 Mock 的缺陷，但它验证了**并发断言本身有效**。
B 的真实实现若也用「先查后写」而无事务/唯一约束，会遇到同样问题。
`tests/test_cet_contract.py -m concurrent` 的四条用例应作为 B 的自检项。

### BUG-006c · 复习条目状态自造枚举 `skipped_pending`，违反契约 7.3

| 字段 | 内容 |
| --- | --- |
| 严重度 | **P1**（契约违规，会让 A 与 B 按不同状态值实现，联调必对不上） |
| 状态 | ✅ **已复验**（C 修复） |
| 归属 | C（Mock 与断言） |

**怎么发现的**：本轮系统核对「契约样例字段是否覆盖任务书第 7 节」时，
把 7.3 规定的枚举值逐条对照 Mock 实际返回值，发现对不上。

**问题**：任务书 7.3 明确「复习条目至少区分 `pending`、`current`、`done`、`skipped`」。
C 的 Mock 在「跳过」时返回的是**自造的 `skipped_pending`**。

**为什么之前没被测出来**：C 自己的断言写成了

```python
assert "skip" in skipped["status"] or skipped["status"] == "pending"
```

`"skip" in "skipped_pending"` 为真，于是**契约违规被松断言放过去了**。
这是本轮最有价值的教训：**断言写成子串匹配，等于没断言**。

**影响**：若不修，A 可能按 `skipped_pending` 判断分支，B 按契约用 `skipped`，
两侧状态值不一致，D2 联调时会出现「跳过之后页面状态不对」且难以定位。

**修复**：
1. Mock 改为返回契约值 `skipped`；
2. 「跳过 ≠ 听懂」的语义**单独用 `needsPractice: true` 表达**，
   不让状态值承载两层含义；
3. 断言改为严格相等 `status == "skipped"`，并检查 `needsPractice`；
4. 新增 4 条枚举合规测试（`test_practice_status_enum`、`test_step_action_enum`、
   `test_review_status_enum_through_lifecycle`、`test_review_item_status_always_in_enum`），
   把「枚举必须落在集合内」变成系统检查，不只盯这一条路径。

**复验**：把 Mock 改回 `skipped_pending` 后，新测试立刻失败并明确指出
`assert 'skipped_pending' in {'current', 'done', 'pending', 'skipped'}`；
恢复修复后 53 项全通过。
