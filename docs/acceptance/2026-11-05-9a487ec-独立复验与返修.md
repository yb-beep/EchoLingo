## P1 · C01 · 同名索引导致上一版数据库升级无效

代码：`backend/webapp/services/cet_service.py:466–471`。部分索引沿用上一版 `cet_attempts_session_uniq` 名称，`CREATE ... IF NOT EXISTS` 不会更新已有索引定义，却把迁移状态登记为 `ok`。

**最短复现：**

1. 构造旧库，已有 `CREATE UNIQUE INDEX cet_attempts_session_uniq ON cet_attempts(material_id,listening_session_id)`，即没有 WHERE 的全量索引。
2. 调用新迁移，读取 `sqlite_master.sql`，仍是旧全量索引，诊断却是 `ok`。
3. 对相同材料提交两个不同 `attemptId`，均不传 `listeningSessionId`，这是执行方明确宣称兼容的旧客户端路径。
4. 真实业务函数返回的两次 `attemptId` 相同，第二次提交未形成独立作答。不是只存在于 SQL 推理的风险。

本轮实测请求 `upgrade-728b6ffirst` 和 `upgrade-728b6fsecond`，两次都返回前者。没有证据表明用户原库已发生此问题；复现均在隔离副本。

**返修要求：**验证已有索引的列与谓词，使用版本化迁移完成无损替换。不得只换名称并保留仍然生效的旧全量索引。新库、无索引旧库、已有旧全量索引、已有正确部分索引均要覆盖；两个空 session、不同 attemptId 的请求应保留为两份作答。

证据：[迁移脚本](./evidence/9a487ec-independent/migration_probe.py)、[迁移与实际提交结果](./evidence/9a487ec-independent/migration-results.json)。

## P1 · C02 · needs_dedup 后仍允许无幂等保护地写新记录

“不删旧数据”这部分修对了：内存构造库中的两条不同版本作答及两份答案全部保留。但历史非空 session 重复时，建索引失败，库继续正常接受新交卷。当前提交逻辑先读、后写，没有索引时并发请求仍可能各建一条。

**本轮实测：**

- 正常副本：6 个请求同材料、同新会话，返回同一 ID，数据库 1 条。
- 另一个副本：只增加两条历史重复记录，使索引创建失败，状态为 `needs_dedup`。对一个完全新的会话并发 6 次，返回 **6 个不同 ID**，数据库也有 6 条。
- 该检查调用真实业务函数、真实 SQLite；仅在读取题目后加线程屏障，确定性制造多个请求同时进入“尚无记录”的窗口，没有伪造 SQL 结果。

因此“新记录并发 6 次只生成 1 条”仅在索引有效的库成立。`attempt_idempotency_state()` 当前只有定义、没有诊断路由/日志调用点，且是进程级变量，不能当成某个库已对外明确报告异常的证据。

**返修要求：**保留历史作答，选择安全的幂等键映射表或等效的事务方案；旧重复记录不能导致新会话失去唯一性。历史重复键的访问应有明确、可追溯的处理语义，不能任取一个。若暂时不能保障，必须明确拒绝相关写入并暴露原因，不能静默继续生成重复记录。

证据：[并发脚本](./evidence/9a487ec-independent/concurrency_probe.py)、[两种库的对照结果](./evidence/9a487ec-independent/concurrency-results.json)。

## P1 · C03 · AI 取消没有稳定终态，也没有绑定被取消的请求

代码：`backend/webapp/services/cet_service.py:1608–1671`、`1511`、`1530`。

完整契约中的 AI 查询测试自身缺 stepId/version，且使用 mock 专属的慢响应参数，不能直接据其失败断言 pending 查询坏了。因此本轮另建有效请求，携带真实 stepId/materialVersion/requestId，在模型调用边界延迟 6 秒。

**实测过程：**

1. 请求 A 成功进入 pending，GET 能返回 A 的 requestId：这部分通过。
2. 取消 A：响应是 `cancelled:true`，但 `aiRequest:null,status:idle`；随后 GET 也只返回 idle，丢失已取消请求的身份及原因。
3. 启动 B，确认 B 为 pending；重发携带 A 的 requestId 的取消请求。接口完全不读 body，实际取消了 B。此时库中 A/B 都是 cancelled。
4. A/B 的模型响应迟到后，都返回 409，步骤未改变：拦截迟到结果这部分通过。
5. 但数据库 A/B 的状态都从 cancelled 被改成 stale；GET 仍只显示 idle。取消终态与取消原因没有保留。

当前 `{}` 表示“取消当前请求”的协议本身也缺安全重试所需的目标身份；不能只在文档里把它称为“幂等”而忽略中间启动了新请求的情况。

**返修要求：**把目标 requestId 或等效的版本条件纳入正式契约。重试取消 A 不得影响 B；取消/失败等终态可查询，并带可区分原因。清理 active 指针与保留请求历史应分别处理。迟到响应只能被拒绝，不能把已取消终态覆盖为 stale。测试应同时断言 API、数据库和当前步骤，并涵盖请求 A → 取消 A → 请求 B → 重试取消 A。

证据：[有效请求探针](./evidence/9a487ec-independent/cancel_probe.py)、[完整响应与数据库状态](./evidence/9a487ec-independent/cancel-results.json)。
