# 实现前必读：契约里容易漏掉的 12 个点

> C 在 D1 期间逐条对照任务书，发现**多个「任务书明确要求、但契约最初没表达」的能力**。
> 这些不是测试没覆盖，而是**契约本身漏了** —— 如果 A、B 照着最初的契约实现，
> 就会一起漏掉，等到联调才发现。
>
> 现在契约已经补齐。这份清单是**实现前的对照表**：每条都说明「为什么容易漏」
> 和「漏了会怎样」。
>
> 适用：A 写前端调用、B 写后端实现时逐条对照。
> 最后更新：2026-11-03｜底座 `1ea5b35`

---

## 一、模型请求必须有可查询状态（7.2 末句）

**任务书原文**：「异步模型操作需要可查询状态或可取消的实现。」

**为什么容易漏**：只做「请求 → 等 → 返回」的同步模型最容易，但那样模型慢时用户只能干等。

**正确做法**：

| 状态 | 含义 | 前端该做什么 |
| --- | --- | --- |
| `idle` | 没有进行中的请求 | 正常显示 |
| `pending` | 请求已发出、未返回 | **显示「正在处理」**，允许取消 |
| `complete` | 成功 | 展示结果 |
| `failed` | 超时/上游错误 | 显示错误 + 重试按钮 |
| `cancelled` | 用户取消 | 回到可操作状态 |
| `invalid` | 模型输出不符契约 | **不得写入步骤**，回退本地动作 |

**接口**：
```
GET  /api/cet/practices/{id}/ai-status   查询状态
POST /api/cet/practices/{id}/ai-cancel   取消（仅 pending 可取消，幂等）
```

**漏了会怎样**：慢网络下带练像卡死；用户无法取消；A 只能编一个假的 loading。

## 二、播完门槛：没播完不计学习时长（7.2）

**任务书原文**：验收列写「播完门槛、重复事件、计时」。

**为什么容易漏**：把 `playedMs` 直接累加很简单，但用户点一下跳过也会被算成学习时间。

**正确做法**：实际播放需达到该步骤音频时长的 **80%**，才算一次有效播放。

```json
// 响应里带上判定过程，便于核对（不要只给最终数字）
"playThrough": {
  "playedMs": 500,
  "expectedMs": 4639,
  "ratio": 0.8,
  "passed": false
}
```

**漏了会怎样**：「十分钟复习」的预算被快速点击消耗掉；有效学习时长失真。

---

## 三、取消后，迟到的模型结果必须被拒（T09）

**任务书原文**：T09「请求后切句、结束或重试 → 旧结果不覆盖当前状态」。

**为什么容易漏**：只在「成功返回」路径上做版本校验，忘了「已取消」这条路径。

**正确做法**：取消后再收到原请求的结果，返回 **409**，且**不得把状态改回 complete**。

**漏了会怎样**：用户取消了，界面却突然弹出结果；或状态从 cancelled 跳回 complete。

---

## 四、模型输出无效时不得推进步骤（D2 要求）

**任务书原文**：「处理无候选、超时、**模型输出无效**、取消、重复提交和过期响应。」

**为什么容易漏**：只处理「请求成功/失败」，没处理「成功但内容不合契约」。

**正确做法**：校验模型输出；不符就拒绝，**不新增步骤、不修改 `currentStepId`**，状态转 `invalid`。

**漏了会怎样**：用户看到半成品内容；坏数据进了步骤历史，复习时重复出现。

---

## 五、复习的「替换」动作（7.2）

**任务书原文**：「完成卡点列表、最新反馈、复习优先级、最多三处排序、**替换**、跳过和结束。」

**为什么容易漏**：`start/switch/skip/done` 看起来够了，容易忽略「替换」。

**正确做法**：
```
POST /api/cet/reviews/{id}/actions
{ "action": "replace", "itemId": "<当前条目>" }
```

语义边界（容易做错的地方）：
- 只能换**当前条目**
- 新条目必须来自**尚未纳入复习**的待练卡点
- 没有可换的 → **明确报错**（`NO_REPLACEMENT` 409），不能静默什么都不做
- 被换下的**不是「完成」**，仍在会话内
- 保留 `replacedFrom` 记录被换下的是哪一处

**漏了会怎样**：用户只能接受系统挑的三处，想换一个不行。

---

## 六、复习条目状态只能用契约枚举（7.3）

**任务书原文**：「复习条目至少区分 `pending`、`current`、`done`、`skipped`。」

**为什么容易漏**：想表达「跳过但仍需练」，很自然会造一个新状态如 `skipped_pending`。

**正确做法**：状态**只用** `skipped`；「跳过 ≠ 听懂」用**独立字段**表达：

```json
{ "status": "skipped", "needsPractice": true }
```

**漏了会怎样**：A 按 `skipped_pending` 判断分支、B 按契约用 `skipped`，
两侧状态值不一致，D2 联调出现「跳过之后页面状态不对」且难定位。

## 七、错误响应有两种形状，必须都处理

**为什么容易漏**：只按自己实现的 `{error, error_info}` 写前端，忘了请求体解析失败时
FastAPI 返回的是 `{detail: [...]}`。

**正确做法**（照底座既有前端 `elt_credits.js:63` 的写法）：

```js
const detail = payload && (payload.detail || payload.error_info || payload);
```

**漏了会怎样**：请求体异常时页面白屏或显示「未知错误」。

---

## 八、句子吸附：吸偏了回听就是错句子（T02/T04）

**为什么容易漏**：断言「有 `suggestedSentenceId`」很容易，验「吸得对」要逐句比。

**正确做法**：
- 按**原始按键秒数**吸附到包含它的句子
- **`pressedAtSec`（原始按键）与 `suggestedSentenceId`（吸附结果）必须分别保留**
- 用户确认后写 `confirmedSentenceId`，**不得覆盖**前两者

**漏了会怎样**：用户回听的是错句子；事后无法追查「是按偏了还是吸偏了」。

## 九、并发下不能产生重复记录（D3 + OBS 要求）

**为什么容易漏**：串行测试永远是通过的，并发要专门压。

**正确做法**：C 在 Mock 里就踩过这个坑 —— `submit_attempt` 用「先查再写」，
并发时两个请求同时通过检查，产生两个 `attemptId`。

| 必须幂等的操作 | 依据 |
| --- | --- |
| 同会话交卷 | 同一 `listeningSessionId` 只产生一个 `attemptId` |
| 同 `eventId` 上报 | 只计一次时，不重复累加 `effectiveMs` |
| 同标记重复创建 | 同一 `eventId` 只产生一个 `markId` |
| 并发 `next` | 结束后 `currentStepId` 必须指向真实存在的步骤 |

**漏了会怎样**：重复记录、重复计时；`-m concurrent` 四条测试会直接红。

## 十、等待与暂停都不计时（T08/T12）

**任务书原文**：T08「等待不计练习时长」；T12「用时不含暂停」。

**正确做法**：只有「前台 + 可见 + 达到播完门槛」的播放才累加 `effectiveMs`。

**漏了会怎样**：用户等待越久「练习时长」越长，与真实学习量脱节。

---

## 十一、未知答案必须保留 unknown（11 节）

**任务书原文**：「未知答案保留未知状态。」

**正确做法**：
```json
{ "answer": null, "answerSource": "unknown", "correct": null }
```
**不得**推断、填充默认值、或判对错。

**漏了会怎样**：把「不知道答案」的题当成答错，用户看到的成绩是编的。

---

## 十二、材料身份用 ID + 版本，不用路径（7.1）

**任务书原文**：「浏览器本地文件路径通过各自配置映射，**不用路径作为材料唯一身份**。」

**正确做法**：身份 = `materialId` + `materialVersion`；音频用哈希核对。
`audioUrl` 是 API 路径，不是本地文件路径。

**漏了会怎样**：换一台电脑路径不同，材料就对不上；同一段音频不同版本混用。

## 附：B 自测前必须知道的两件事

### 1. 底座测试有既有污染，别被吓到

`create_app()` 内部调用 `db.init_db()`（无参数），走 `current_db_path()` 的回落链，
**绕过测试的 `monkeypatch.setattr(db, "DB_PATH", ...)`**。

所以如果你改了 `create_app()` 或 `db`，自测时请：

```bash
ELT_USER_DB=/tmp/my-test.db .venv/bin/python -m pytest tests/  -q
# 或先删掉 resources/vocab.db 再跑
```

否则会看到大量与自己改动无关的失败。详见问题清单 **OBS-003**。

### 2. 底座有 61 个既有失败，别拿「全量通过」当门槛

```bash
pytest tests/ -q --ignore=tests/test_cet_contract.py
# → 61 failed, 446 passed（既有基线，非本改造引入）
```

**看「新增失败」，不看「有没有失败」。**
