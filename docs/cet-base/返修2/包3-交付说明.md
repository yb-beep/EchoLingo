## 2. P3-2 · 说话人标记清洗（✅ 完成）

### 2.1 缺陷与真实根因（与文档说法不同，以实测为准）

任务书说「第 23 句是 `/ W: What?`，文档写 32 句，精听页显示 33 句」。
**实测确认了现象，但根因不是落库条数**：

- 落库 `v2_subtitle_segments` **一直是 32 条**（与文档一致）；
- `/api/v2/lessons/{id}/subtitles` 的 `sentence_units` 是 **33** 条。

原因是源数据 `cet6-202512-conv2.sentences.source.json` 第 22 条的 `text`
末尾**粘着下一位说话人的整句**：

```json
"text": "When we are done with it and send it upstairs, what do you think will happen? / W: What?"
```

而第 23 条自己就是 `"What?"`。`build_translation_units()` 把第 22 条按标点再切一次，
于是多出一条以 `/ W:` 开头的「句子」—— 这才是「精听页比文档多一句」的来源。

### 2.2 修复

| 位置 | 内容 |
| --- | --- |
| `cet_import.split_speaker_markers()` | 按标记切句并剥掉标记本身。认三种形态：`/ W:`（句中/行首都算句界）、行首裸 `W:`、行首孤立 `/ `。**只认单个大写字母**（`Note:` / `OK:` / `Ratio A:` 不动） |
| `cet_import._apply_speaker_cleaning()` | 整份清洗 + **标记回声去重**：拆出的尾巴若与下一条逐字相同 → 是回声，丢弃尾巴；标记仍记入报告 |
| `cet_import.clean_sentences()` | 公开入口，给 `scripts/cet/import_materials.py` 用（保证脚本与界面**同一份规则**） |
| `prepare_subtitle()` | 清洗接在**解析后、校验前**（清洗会重新分配被拆条目的时间轴，先校验会看到与落库不同的数据） |
| `_write_speaker_markers()` | 标记写 `output/v2_assets/<lesson_id>/speaker_markers.json` sidecar |
| 纯文本分支 | **先按行清洗再分段**（否则 `split_plain_text` 合并行后段中间的 `M:` 剥不掉） |

**为什么用 sidecar 而不是新列**：冻结约定 §3 明确「不新增表、不新增列」，
而任务书 P3-2 要求「保留在元数据里不丢」。sidecar 两者都满足。

| 材料 | 落库 `segments` | `sentence_units` | 一致？ |

## 3. P3-1 · 本地模型自动切句（✅ 完成）

### 3.1 三条硬约束（前端 + 后端双保险）

| 约束 | 前端 | 后端（**不只靠前端**） |
| --- | --- | --- |
| **默认不勾** | HTML 不写 `checked`；`cetResetImport()` 归零 | `auto_split: bool = False` 默认值；不勾时 `autoSplit.queued === false` 且**零副作用** |
| **有字幕时不可勾** | `disabled` + 说明「本地转写会覆盖你上传的字幕时间轴」 | **422 硬拒**，`reason=auto_split_conflicts_with_subtitle`，且**不留任何材料/上传** |
| **`faster_whisper` 不可用灰掉** | 读 `/import/formats` 的 `autoSplit.available` | 同一份探测；直接调 API 也 422 `auto_split_unavailable` |

「有字幕时禁用」是从根上避开竞态：不是「尽量别覆盖」，而是这条请求**根本不允许存在**。

### 3.2 两条路径：有原文优先文本对齐

| 附件 | 路径 | 句子文本来源 |
| --- | --- | --- |
| 音频 + TXT | **文本对齐** `text_alignment` | **用户原文逐字不改**，只补时间轴 |
| 仅音频 | **纯转写** `transcribe` | 本地 ASR 结果 |

### 3.3 ⚠️ 没有照抄任务书提示的 `start_local_lesson(transcript_path=...)`（附理由）

任务书提示走 `start_local_lesson(transcript_path=...)` / `_import_local_media` 那条。
**实测这条路走不通**：

- `start_local_lesson` → `enqueue_local_import` → `sources.baidu.build_local_video_lesson`
  → `parse_subtitle_file(transcript)`；
- 而 `parse_subtitle_file` **只认 SRT/VTT 的 `-->` 行，喂纯文本返回空列表**。

实测：

```python
>>> from sources.subtitle_parser import parse_subtitle_file
>>> parse_subtitle_file(Path('plain.txt'))   # 内容 "Hello there. This is plain text.\nSecond line here.\n"
[]
```

所以「把 TXT 当 `transcript_path` 传进去」会得到一个**空时间轴**，
既不是文本对齐也不是转写，是个静默失败。

本包的实现：`_transcribe_words_local()` 取词级时间戳 →
`align_text_to_words()`（`difflib.SequenceMatcher` 对齐原文词序列与 ASR 词序列，
思路同 `mfa_alignment.project_words_to_sentences` 但**独立实现**，因为那个函数
吃 `translation_units` + MFA 风格词、还带 `coverage>=0.55` 阈值与 `pause_*` 计算，
自动切句只需要每句起止）→ `build_segments_from_text_alignment()`。

另外**没有复用** `start_uploaded_media_lesson()`：它末尾会 `enqueue_local_import()`
无条件排转写，正是 §3.5 记录的覆盖竞态来源。继续用
`_create_lesson_from_upload()`（返修前就有，只复用原语不排转写）。

### 3.4 进度复用现有状态枚举（不新造）

| 阶段 | `subtitle_status` | 前端文案 |
| --- | --- | --- |
| 排队 / 转写中 | `pending` | 正在准备原文 |
| 成功 | `ready` | 可逐句精听 |
| 失败 | `failed` + `subtitle_error` 具体原因 | 原文准备失败 |

失败**不弹「字幕失败」诱导重试**：`subtitle_error` 里是具体原因，例如
「自动切句失败：模型加载失败：磁盘空间不足」「自动切句失败：课程音频文件不可读，无法自动切句」
「自动切句失败：本地模型没有识别出任何语音内容（录音可能全是静音）」。
**不会留 `pending` 悬挂**（异常分支一定写 `failed`）。

## 5. P3-3 · 百度网盘初始化定位（✅ 定位完成，按任务书「只报告不改」）

### 5.1 定位结论

**初始化发生在应用启动的公共代码里，不在本包文件范围 → 只报告不改。**

| 位置 | 代码 | 说明 |
| --- | --- | --- |
| `backend/fastapi_server.py:163-174` | `create_app()` 的 `lifespan` 上下文 | 应用启动钩子 |
| `backend/fastapi_server.py:166-167` | `from webapp.services import baidu_pan`<br>`baidu_pan.init_queue()` | **无条件调用**，没有任何 feature 判断 |
| `backend/webapp/services/baidu_pan.py:215-228` | `init_queue()` | 打开 jobs DB + 恢复任务 + `_ensure_workers()` |
| `backend/webapp/services/baidu_pan.py:137-144` | `_jobs_db_path()` | `ELT_BAIDU_PAN_JOB_DB` → `ELT_CONFIG_DIR/baidu_pan_jobs.db` → `<repo>/resources/baidu_pan_jobs.db` |
| `backend/webapp/services/baidu_pan.py:148-152` | `_jobs_db()` | `path.parent.mkdir()` + `sqlite3.connect()` → **这一步创建了 `baidu_pan_jobs.db`** |

所以「演示配置目录里出现 `baidu_pan_jobs.db`」的直接原因是：
`lifespan` 无条件调 `init_queue()` → `_jobs_db()` 在 `ELT_CONFIG_DIR` 下建库。

### 5.2 建议修法（供主代理/包5 或后续处理，**本包未改**）

`backend/fastapi_server.py` 不在本包文件所有权内（任务书 §1 表格里它没分给任何包，
属于主代理/公共代码）。建议改为：

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    from webapp import cet_mode
    # 链接导入（含百度网盘）在 CET 模式已收束 → 不再初始化退役服务
    if cet_mode.feature_enabled("link_import"):
        from webapp.services import baidu_pan
        baidu_pan.init_queue()
    ...
```

`cet_mode.feature_enabled("link_import")` 在 CET 模式下返回 `False`（`_FEATURES`
里 `link_import.kept = False`），通用模式返回 `True`（全部保留），
正好符合「CET 模式不初始化、通用模式行为不变」。

`ELT_CET_FEATURE_LINK_IMPORT=1` 仍可显式打开，验收时想测网盘功能不受影响。

**替代方案（更小改动，但语义差一点）**：给 `init_queue()` 加
`if os.environ.get("ELT_BAIDU_PAN_ENABLED", "1") != "1": return` 早退 ——
但这要求部署方记得设环境变量，不如按 feature 判断可靠。
