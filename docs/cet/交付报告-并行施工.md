## 4. 各板块关键成果

### A 板块：D01 幂等全入口

**原缺陷**：幂等占位写在 `if not attempt_id` 块内，客户端自带 `attemptId` 时绕过。
在有历史重复的库中，同一会话并发 6 次生成 6 个 ID。

**修复**：幂等解析提到前置，两种 ID 入口共用。
历史重复**一条不删**（answers 是 CASCADE），返回最早一条 + `conflict: true` + `conflictDetail`。

**实测**：
```
正常库+服务ID 并发6 → 1 条
正常库+客户端ID 并发6 → 1 条
重复库+服务ID 并发6 → 0 新增
重复库+客户端ID 并发6 → 0 新增  ★原缺陷场景
空 session 不同 ID → 保留 2 条
```

**AI 生命周期**：`_cancel_pending_ai` 的 status 改关键字必传；
`_late_ai_result_terminal` 按 `error_code` 区分：
`pending→stale`、`failed(SERVER_RESTARTED)→stale`、`failed(其他)→不动`、
`cancelled→不动`、`succeeded→不动`。

### B 板块：D02 受控模型 + D03 契约统一

**D02 的关键**：上一版 fixture 固定返回跨句短语，被生产校验器全部拒绝
（32 句 0 成功）。所以「无 key 与受控模型都是 33/39」只是两种失败的重合，
**成功路径从未跑通**。

本版从输入原句派生合法短语与分段，经真实 `cet_ai.generate()` 验证：
explain **32/32**、chunk **31/31**。唯一例外 `"What?"`（1 词）在
「2–4 段、每段 ≤8 词」下无法合法分段，返回 `None` 抛错，**不伪造响应**。

**D03**：事件七种（含前端依赖的 `visibility`/`transfer_answer`）、
双键返回、状态枚举分离、构造器补字段。

## 5. 本轮修的协作事故（如实记录）

### 事故 1：分支污染

**现象**：主代理切分支时未检查 HEAD，两个提交落进子代理 B 的分支。
**发现者**：B 板块施工者（主动报告并保全）。
**修复**：cherry-pick 回主分支；新增「分支纪律」章节（操作前先 `git branch --show-current`、
子代理只在 worktree 提交、合并后立即验证 HEAD）。

### 事故 2：数据污染归因反复

**现象**：`v2_tags` 序列从 30 漂到 2460。

**归因过程（三次反复，值得记录）**：
1. 我说「脚本污染」——方向对但没量化
2. B 更正「纯属应用正常行为」——它的 `INSERT OR IGNORE` 消耗实验是对的，
   但没解释 2460 这个量级
3. B 撤回，回到「脚本污染」——还是没量化
4. **最终我用「单次消耗 30 × 81 次」定量确认**：两因素叠加，
   `init_db()` 是消耗源（每次 30），脚本是放大器（跑 81 次）

**真实库状态**：CET 表 0 张、`v2_tags` 30 行无重复、序列已重置 → **数据完好**。

**教训**：报数据事故前先做**对照实验 + 量化拆解**，不要只看一个数字；
也不要因为「某人做了实验」就采信，要看实验是否覆盖了量级。
