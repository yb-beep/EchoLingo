## 2. 实测污染事件（已修复）

### 现象

不加隔离直接跑 `pytest -q`，正式库会被改写：

| 时间 | 现象 |
| --- | --- |
| 首次发现 | md5 由 `d2c9f472…` 变为 `81316370…` |
| 连续跑 | `v2_media_uploads` 从 5 行涨到 30 行（每次全量跑 +25 条） |

### 根因（两条，必须同时处理）

**A. 仓库根 `.env` 在 import 期注入 `ELT_USER_DB`**

`.env` 里写着 `ELT_USER_DB=<仓库>/.cet-qa/data/vocab.db`。
`backend/analyzer.py:80` 与 `webapp/runtime/ai_config.py:31` 在 import 期就执行
`load_dotenv()`，把它写进 `os.environ`。

**B. `ELT_USER_DB` 优先级高于测试的 monkeypatch**

`backend/db.py` 的 `current_db_path()` 解析顺序：

```
contextvar → ELT_USER_DB → DB_PATH
```

绝大多数测试用 `monkeypatch.setattr(db, "DB_PATH", tmp_path/"vocab.db")` 隔离，
但 env 优先级更高 —— monkeypatch 被静默覆盖，测试写进共享库。

实测探针：
```
DB_PATH attr      = /tmp/PROBE-monkeypatched.db
current_db_path() = /tmp/probe-env.db          ← env 赢了
```
单文件对照：`tests/test_vocab_review.py` 不设 env → 23 passed；设 env → 10 failed。

### 修复（`tests/conftest.py`，提交 `10f1eb6`）

三道护栏：

1. import 期摘掉 `ELT_USER_DB`
2. `db.DB_PATH` 指向**正式库副本**（不是空库——部分测试依赖 `v2_tags` 的 30 行种子）
3. 每个用例开始前再摘一次 env（防用例内部 import 重新触发 `load_dotenv`）

### 验证

护栏后的验证见 §5：**只读逻辑快照**前后完全一致（不是「行数相同」）。

**失败教训（勿重蹈）**：
- 第一版每用例换 `DB_PATH` → 61 failed（破坏依赖种子数据的用例）
- 第二版空库 → 46 failed

## 3. 残留的边界：SQLite 文件字节会变，数据不会变

即使数据零写入，`resources/vocab.db` 的 **md5 也可能变化**。

原因：正式库是 **WAL 模式**（`journal_mode=wal`）。任何进程以读写方式打开它
（哪怕只读不写数据），SQLite 都可能重写文件头/页元数据，导致 md5 变化。

**实测（本机，2026-11-05）**：拿正式库副本，仅做「打开 → 切 journal_mode → 关」，
不写任何一行数据：

```
md5 before: 813163706319ef5f8a456b1dd00f63c0
md5 after : 07ab9827a1581e18d3ea2110e5f2aed9     ← 变了
逻辑快照 digest 相同: True                        ← 数据没变
```

**结论：md5 变化不能证明数据被改，md5 不变也不能证明数据没被改**（见 §4.2）。
它只能作为「文件字节是否有任何变动」的辅助观察，不能作为数据完整性的判据。

## 4. 为什么不能只用行数证明「内容未变」

> 这一节直接回应独立验收意见：
> 「正式库隔离文档不能仅用行数相同证明内容未变；如需证明应核对只读逻辑快照/关键字段内容。」

### 4.1 行数相同 ≠ 内容相同（实测反例）

拿正式库副本，**只改一行内容、不动行数**：

```python
UPDATE v2_tags SET name = name || '_POLLUTED' WHERE id = (SELECT id FROM v2_tags LIMIT 1)
```

实测结果：

```
总行数 before: 36
总行数 after : 36
总行数相同: True              ← 行数判据在这里完全失效
逻辑快照 digest 相同: False   ← 逻辑快照抓到了
v2_tags 行数相同: True
v2_tags sha256 相同: False    ← 表级哈希也抓到了
```

这就是验收方批评的那个漏洞：**行内值可以在行数不变时被更新**。
「36 行还是 36 行」这种判据，对一个被 `UPDATE` 污染的库会给出「未变」的错误结论。

### 4.2 md5 也不行

见 §3 实测：不写数据的正常打开就能让 md5 变；反过来，只要 WAL 里还有未 checkpoint
的页，数据已经变了而主库文件 md5 可能还没变。

### 4.3 那用什么

**只读逻辑快照**：每张表导出全部行内容、算哈希，再对所有表哈希汇总成一个 digest。
比对 digest 即比对**逻辑内容**，与文件字节布局、WAL 状态、页元数据无关。

## 5. 只读逻辑快照（推荐判据）

### 5.1 取快照

把下面这段存成任意本地脚本（例如 `/tmp/db_snapshot.py`），或直接内联执行。
它**只读打开**（`mode=ro`），不写库、不触发 WAL 重写：

```python
# 方案 A：只读打开（mode=ro），不写库、不触发 WAL 重写
import sqlite3, hashlib, json, sys

def logical_snapshot(path):
    con = sqlite3.connect(f"file:{path}?mode=ro", uri=True)
    out = {}
    tables = [r[0] for r in con.execute(
        "select name from sqlite_master where type='table' "
        "and name not like 'sqlite_%' order by name")]
    for t in tables:
        rows = [tuple(r) for r in con.execute(f'select * from "{t}" order by rowid')]
        blob = json.dumps(rows, ensure_ascii=False, default=str, sort_keys=True)
        out[t] = {"rows": len(rows),
                  "sha256": hashlib.sha256(blob.encode()).hexdigest()}
    digest = hashlib.sha256(json.dumps(out, sort_keys=True).encode()).hexdigest()
    return {"digest": digest, "tables": out}

print(json.dumps(logical_snapshot(sys.argv[1]), ensure_ascii=False, indent=2))
```

> 说明：BASE-04 返修范围限定在启动/停止脚本层，本轮**没有**新增
> `scripts/qa/db_snapshot.py`。请把上面这段保存到你自己的临时目录使用。

#### 5.1.1 方案 B（备选）：`mode=ro` 打不开时改「先 cp 再普通打开」

**什么时候用**：本机实测过 `mode=ro` 报错的情况——

```
sqlite3.OperationalError: unable to open database file
```

或（WAL 库 + 所在目录不可写时）：

```
sqlite3.OperationalError: attempt to write a readonly database
```

原因是 `resources/vocab.db` 是 **WAL 模式**（`pragma journal_mode` 实测返回 `wal`）。
只读连接打开 WAL 库时仍需在**同目录**创建/映射 `-shm` 与 `-wal` 辅助文件；
目录不可写（或 `-shm` 状态异常）就会报上面两条错。这不是库坏了，是只读 URI
在 WAL 下的已知边界。

**备选写法**：先 `cp` 一份到可写的临时目录，再**普通打开副本**计算。
`cp` 对源文件是纯只读操作，不打开 SQLite 连接、不写源库；
算出来的逻辑快照与方案 A **完全相同**。

```python
# 方案 B（备选）：先 cp 到临时目录，再普通打开计算（结果与方案 A 相同）
import sqlite3, hashlib, json, os, shutil, sys, tempfile

def logical_snapshot(path):
    tmpdir = tempfile.mkdtemp(prefix="db-snapshot-")
    dst = os.path.join(tmpdir, "vocab.db")
    # 只做 cp：源文件只读操作，不打开、不写源库
    shutil.copy2(path, dst)
    try:
        con = sqlite3.connect(dst)          # 普通打开副本，不碰源库
        try:
            out = {}
            tables = [r[0] for r in con.execute(
                "select name from sqlite_master where type='table' "
                "and name not like 'sqlite_%' order by name")]
            for t in tables:
                rows = [tuple(r) for r in con.execute(f'select * from "{t}" order by rowid')]
                blob = json.dumps(rows, ensure_ascii=False, default=str, sort_keys=True)
                out[t] = {"rows": len(rows),
                          "sha256": hashlib.sha256(blob.encode()).hexdigest()}
            digest = hashlib.sha256(json.dumps(out, sort_keys=True).encode()).hexdigest()
            return {"digest": digest, "tables": out}
        finally:
            con.close()
    finally:
        shutil.rmtree(tmpdir, ignore_errors=True)

print(json.dumps(logical_snapshot(sys.argv[1]), ensure_ascii=False, indent=2))
```

**本轮实测（2026-11-06，返修2 包5）**：两方案在同一份库上算出的 digest 完全一致，
都等于基线 `92b86dbaceb711b0a244d6e0b447d8fdb042c9c905dfae0894c095f24a3f9dc4`。

```

# 方案 B（先 cp 再普通打开）
$ .venv/bin/python /tmp/db_snapshot_cp.py resources/vocab.db | head -2
```

> 指回 `resources/vocab.db` 本身，那样就成了普通打开正式库。

### 5.4 给验收方的操作建议

```bash
# 0) 先把 §5.1 的脚本存到 /tmp/db_snapshot.py（一次性）
#    若 mode=ro 在本机报错，改用 §5.1.1 的方案 B（先 cp 再普通打开），两者结果相同

# 1) 跑测试前取一次快照
.venv/bin/python /tmp/db_snapshot.py resources/vocab.db > /tmp/prod-before.json

# 2) 跑你的测试
ELT_CONFIG_DIR=/tmp/<x> .venv/bin/python -m pytest -q \
  --ignore=tests/test_cet_listening_ui.py --ignore=tests/test_cet_contract.py

# 3) 跑完再取一次
.venv/bin/python /tmp/db_snapshot.py resources/vocab.db > /tmp/prod-after.json

# 4) 比对 digest 与逐表哈希（不看行数、不看 md5）
.venv/bin/python -c "
import json
a = json.load(open('/tmp/prod-before.json'))
b = json.load(open('/tmp/prod-after.json'))
print('整体一致:', a['digest'] == b['digest'])
diff = [t for t in set(a['tables']) | set(b['tables'])
        if a['tables'].get(t) != b['tables'].get(t)]
print('差异表:', diff or '无')
"
```

若 `差异表` 非空，那就是**真实的数据变更**，逐表比对 `sha256` 即可定位到具体表；
再结合 `rows` 判断是「新增/删除行」还是「行内值被更新」。

## 6. 本轮不提出任何删除正式库的建议

**上一版本文档曾写「想彻底避免碰正式库，可先备份再删」——该建议已删除。**

理由（接受验收方意见）：

1. **这不是施工方该替用户做的决定。** 正式库属于用户资产，即使当前内容只是
   开发期残留，也只有用户有权判断它是否可以消失。
2. **「没有真实用户数据」是当前时点的观察，不是永久属性。** 用户随时可能在这个库
   里产生真实学习记录；一份写着「删除无损失」的文档会变成误导。
3. **删除会掩盖问题而不是解决问题。** 隔离的目标是「测试不写正式库」，
   这应该由 conftest 护栏和 `ELT_USER_DB` 的正确用法保证（§2），
   而不是靠「把正式库删掉所以没得写」。
4. 验收方明确指出这一点，本轮照改，不再保留任何删除建议。

**替代做法（若确实担心）**：不要删，改为在跑测试前用只读快照留证（§5），
跑完比对。若发现真实变更，按 §2 的护栏路径排查，而不是清库。
